**2026-10-12, third pass: three symptoms, one chain, and a measurement trap of my own.** Graham: *"If I start 'allspeak server' then go to http://localhost:8080/viz.html, a popup says 'viz has been updated. Restart to apply changes?'. I click OK and get 'Please restart the server manually'. So I Control+C the server but the process keeps running."* Reproduced end to end with a scratch rig on a private port (`/version` → `updated`; `/restart` → **a closed connection with no response, 7 times in 8**; the port still serving after the original exits), and the three symptoms turn out to be one chain.

**(1) The nag fired when a restart could not help.** `/version` compared the *running* script with the *published* one and called any difference `updated` — but the caller's question is "should I offer the reader a restart?", and the running copy is one of two things: the CLI's fetched cache, which a restart *replaces*, or a file beside the project, which a restart re-runs byte for byte. Graham runs the server out of a **checkout**, whose script is *ahead* of the published one, so he was offered an update that did not exist. The route now answers `updated` only when the running copy is the CLI's cache; a project's own copy answers `OK`. **Two words and not three, deliberately**: `allspeak viz`'s probe accepts exactly this route's vocabulary, so a third word would be read as "not a dev server" by an installed CLI — and that path's advice ("use another port") starts a *second* server. The route's contract is now stated the way the caller asks it: **`OK` means "nothing for you to do about this process"**.

**(2) The restart's answer was lost.** `return \`OK\` to Files` hands the response to the request thread to write; `exit` on the next line ended the process first. The page's `or` clause therefore reported a failure that had not happened. A `wait 1 second` between them fixes it: **7 of 8 calls lost the reply before, 5 of 5 arrive now.**

**(3) "The process keeps running" is the restart's own child, and the restart is not broken.** `system background` leaves a *detached* server, so the Ctrl+C that follows has nothing to stop — the original had already exited, and its successor is not in the terminal's foreground group. A plain server exits cleanly on SIGINT. **Graham's call, the same day: take the restart out.** *"given that this is an infrequent operation to perform"* — so the page's dialog is now an `alert` that names the reader's own two steps (stop the server, start it again, reload the page), `/restart` is **gone from `server.allspeak`**, and `StrRestart` with it in all four languages. The thing that was on the table and was not taken is written down in `TODO-viz.md` so it is not re-derived: an in-process `exec`-style keyword would have kept the feature *and* the terminal (same pid, still the foreground job, Ctrl+C working) for one new dev-environment keyword in both runtimes, the four packs, a spec note and a check. `confirm` became `alert` because there is no longer an action for the page to take.

**And the trap, which cost me a wrong diagnosis and is worth more than the three fixes.** My first test sent SIGINT to a server started with `nohup … &` and it survived — which looked exactly like the reported fault. It was the harness: a shell with job control off sets SIGINT to **SIG_IGN** in a background child, so the signal was never delivered. `grep SigIgn /proc/<pid>/status` settled it in one line. **A signal test has to prove the signal can arrive** — read the disposition, or install `signal.default_int_handler` explicitly — or it is measuring the harness rather than the program. (I then nearly "fixed" the wrong `/version` branch polarity too, and the rig caught that as well: the first version of the change answered `updated` for a project's own copy.)

**Measured after the fix, four cases:** a checkout → `OK`; a project's cache copy differing from the published one → `updated`; a cache copy identical to it → `OK`; the fetch unreachable → `error`. `/restart` answers `200 OK` in 5 of 5.

### How this list is run

**Sorted by what each item asks of *you*, because that is what had gone wrong: the list had grown to nineteen bullets of which most needed no decision at all.** Four bins, and an item may enter only if it belongs to one of them:

- **Guard — a check that stops the class.** Where a one-off fault is really a *class*, the fix is a check that refuses it, so the class stops generating list entries at all. Two were added today; one is proposed.
- **Note — a fact the code cites.** No action, ever. Notes are allowed to go stale without ceremony: the evidence is in git and in `conversation/`, and a Note that turns out to matter will surface as a fault.

**The admission rule, and it is the anti-growth mechanism.** An item may be written down only if it is (a) decided and unbuilt, (b) a fork with a named owner, or (c) a fact the code cites. "Somebody should look at this" is not admissible — it goes in a Note or nowhere. And an item that has been *done* **leaves** the list; the record is the commit and `conversation/`, not a tombstone.

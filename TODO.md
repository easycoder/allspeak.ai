### How this list is run

**Sorted by what each item asks of *you*, because that is what had gone wrong: the list had grown to nineteen bullets of which most needed no decision at all.** Four bins, and an item may enter only if it belongs to one of them:

- **Decide — yours**, and each says whether it is a *fork* (a choice I should not make for you) or *your own hand* (a sign-off, a deletion, a look at a picture).
- **Do — mine, queued.** No design question; the smallest first step is named. I work these and report. **They are not waiting on you**, and you should not feel they are accumulating — a queued item that never gets picked up costs nothing.
- **Guard — a check that stops the class.** Where a one-off fault is really a *class*, the fix is a check that refuses it, so the class stops generating list entries at all. Two were added today; one is proposed.
- **Note — a fact the code cites.** No action, ever. Notes are allowed to go stale without ceremony: the evidence is in git and in `conversation/`, and a Note that turns out to matter will surface as a fault.

**The admission rule, and it is the anti-growth mechanism.** An item may be written down only if it is (a) decided and unbuilt, (b) a fork with a named owner, or (c) a fact the code cites. "Somebody should look at this" is not admissible — it goes in a Note or nowhere. And an item that has been *done* **leaves** the list; the record is the commit and `conversation/`, not a tombstone.

### Notes the code points at

Four source files cite this file by name, so these stay here until the citations are changed. Both are facts about current behaviour, not history.

- **A published `.py` is *executed* by the site, not served.** Measured 2026-10-04: `/code/tools/asdoc-check.py` answered `500` while the `.js` tools came back as text — which is why both Python tools are published as `.txt` and saved under a `.py` name at the other end. - **The `deploy/` copies are stale until the next deploy, by design.** `deploy/code/*` (the editor, `server.allspeak`, `viz.html`, the version), `deploy/learn/*` and `deploy/codex/*` are refreshed by `./deploy-allspeak` and `./deploy-sync`; the doc-block counts and any "the file differs from the root" observation therefore include copies that are days behind their source. Not a fault, and not a task — but a *measurement* taken over the whole tree will include them.

- **A recording covers a run up to its first `wait`.** `wait` hands the rest of the program to a timer, so `AllSpeak_Run.run` returns and a capture made inside a call covers only that slice; the JS host writes its trace one slice in, and its guard's `stopped` never reaches the file, where Python's host waits for the run to end. Rather than pass a slice off as a whole run, `record … reporting <verdict>` answers with the flag and the status line says so. **`recorder.parked`** — set as the recorder ticks each command, from the same waiting-keyword list the guard uses — is the fact a fix needs. Cited by `js/plugins/asviz.js`, `viz.allspeak` and `tools/guard-check.js`.
- **The heat's per-line counts are the view's own, and the editor's are keyed one line off.** `asviz.js`'s anchors name the *label's* line and its `line_counts` key the *command's* line, so on a wide recording an anchor and its count can name different lines — a mark's colour was its neighbour's heat. The view no longer reads them at all: `VizSeen` counts arrivals itself during the mark pass. Anything else that reads `line_counts` should know it. Cited by `viz-graph.allspeak`.
